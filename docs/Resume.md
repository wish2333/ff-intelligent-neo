### 1.1 项目背景

实习期间，我所在团队面临一个典型场景：上千条视频需要统一更新片头片尾。我主动向主管了解了公司在这块的业务需求和效率要求，主管明确表示这类重复性操作占用了大量人力，希望找到批量处理方案。同事们使用剪映等非线性编辑软件逐条手动操作，大量时间消耗在重复性的导入-裁剪-导出流程上，严重挤占了本应用于创意剪辑和运营策划的精力。调研后发现，虽然 FFmpeg 可以通过命令行高效完成这类批量操作，但团队中没有人能熟练使用 FFmpeg，而市面上的图形化工具（如格式工厂、HandBrake）仅提供基础的转码和滤镜配置，既没有充分考虑滤镜组合与参数冲突的处理（导致实际业务中经常生成无效命令），也未对常用编解码器进行优先级排序和场景化推荐，用户面对几十个编码器和大量参数选项时完全不知道各该设多少，使用门槛反而比命令行更高。

我决定开发一款面向实际业务场景的 FFmpeg 批量处理桌面工具，重点解决现有 GUI 工具在"滤镜组合冲突处理"和"编码器场景化推荐"两个维度的缺失，同时将批处理、配置复用、任务控制作为核心能力，让非技术背景的同事也能高效完成批量视频处理任务。

### 1.2 用户画像

- **实习期间的运营同事**：需要批量更新上千条视频的片头片尾，目前使用剪映逐条手动操作，重复劳动挤占了创意剪辑和运营策划时间
- **同学和课程小组**：需要批量压缩课程录像、统一转码格式以便分享和归档，但不熟悉 FFmpeg 参数
- **校园媒体社团成员**：需要快速剪辑、合并多段视频、混合音频字幕，现有 GUI 工具的滤镜配置太基础且不考虑组合冲突，实际使用中频繁生成无效命令

## 2. 痛点与动机

### 痛点

- **FFmpeg 命令行门槛高**：转码、滤镜、剪辑等操作需要记忆几十个参数，同事和同学往往需要反复查阅文档才能拼出正确的命令，而实习期间的批量视频处理任务对效率有硬性要求，命令行方式完全不可行
- **现有 GUI 滤镜配置过于基础，未考虑组合与冲突**：市面上的 FFmpeg 图形化工具（如 HandBrake、格式工厂）仅提供单项滤镜开关，缺乏对滤镜链组合顺序、参数互斥冲突（如旋转与宽高比转换同时启用时参数矛盾）的处理能力，导致在实际业务中经常生成无效命令或输出异常文件，根本无法用于生产环境，更不用说在此基础上实现批处理与配置复用
- **编解码器缺乏优先级排序与场景化推荐**：FFmpeg 提供数十种编码器和大量参数选项（CRF、preset、像素格式等），现有工具只是简单罗列所有选项，没有根据使用场景（如社交媒体发布、存档压缩、快速剪辑）进行分组推荐和默认值设定，用户完全不知道各参数该设多少合适，进一步拉高了使用门槛
- **批处理与配置复用能力缺失**：每次处理相似任务（如统一更新片头片尾）都需要逐条手动操作，无法保存配置模板批量应用，上千条视频的重复劳动严重挤占了创意工作时间

### 改善

- **降低使用门槛**：图形化配置覆盖 20+ 编码器并按场景分组推荐（推荐编码器 / GPU 硬件加速 / 其他 / 自定义），6 种滤镜支持组合链且自动处理互斥冲突，实时命令预览让用户直观看到生成的 FFmpeg 命令
- **批处理效率提升**：任务队列支持独立暂停/恢复/停止/重试，配合批量操作，上千条视频的片头片尾更新从逐条手动剪辑变为配置一次批量执行，将重复性操作时间压缩约 70%
- **配置一键复用**：预设系统支持保存和加载编码器+滤镜+剪辑配置组合，相似任务无需重复配置，直接套用预设即可批量执行
- **实时进度感知**：进度条、处理速度、FPS、预估剩余时间等实时显示，任务状态变化自动刷新，长时间批处理时用户可以随时掌握进展

## 4. 产品方案

### 4.1 方案概述

FF Intelligent Neo 是一款跨平台桌面 FFmpeg 批量处理工具，核心价值是将复杂的 FFmpeg 命令行操作转化为直观的图形化配置，同时提供完整的任务队列管理和实时进度反馈。产品围绕 7 个功能模块组织：

| 模块 | 核心能力 |
|------|---------|
| 任务队列 | 批量添加文件、独立暂停/恢复/停止/重试、批量操作、状态持久化 |
| 命令配置 | 20+ 编码器选择、转码参数配置、6 种视频滤镜、实时命令预览 |
| 视频剪辑 | 时间范围剪辑（cut）、片头片尾提取（extract）、无损剪辑 |
| 音频字幕混合 | 替换/添加外部音频轨和字幕文件 |
| 视频合并 | concat 和 filter_complex 两种模式，支持片头片尾追加、拖拽排序 |
| 自动剪辑 | 基于 auto-editor 的静音/运动检测自动剪辑，基础/高级双模式 |
| 自定义命令 | 直接编写 FFmpeg 原始参数，配合 ffprobe 文件分析 |

### 4.2 核心功能设计

#### 功能一：可视化 FFmpeg 命令构建器（含滤镜组合冲突处理与编码器推荐）

- **做什么**：用户通过表单选择编码器、配置转码参数、添加滤镜链，系统自动处理滤镜互斥冲突（如旋转与宽高比转换互斥）、实时生成完整的 FFmpeg 命令并预览；编码器按场景分组推荐并预设默认参数值
- **为什么这样设计**：直接对应"现有 GUI 滤镜配置太基础不考虑组合与冲突"和"编解码器缺乏优先级排序与推荐"两大痛点，让用户无需理解 FFmpeg 参数体系也能生成正确的命令
- **关键设计决策**：采用声明式配置模型（TranscodeConfig + FilterConfig + ClipConfig），后端 command_builder 根据配置对象构建命令并校验互斥关系，而非前端拼接字符串；编码器注册表按"推荐 / GPU 硬件加速 / 其他 / 自定义"分组，每组预设 CRF、preset 等推荐值，降低参数选择门槛

#### 功能二：线程安全任务队列

- **做什么**：支持批量添加任务、独立控制（暂停/恢复/停止/重试）、状态持久化与启动恢复
- **为什么这样设计**：对应"批处理能力缺失"的痛点，让上千条视频的重复操作从逐条手动变为配置一次批量执行
- **关键设计决策**：使用 ThreadPoolExecutor + threading.Event 实现任务并行与取消控制；Task 模型使用线程锁保护状态变更；队列状态通过原子写入持久化到 JSON 文件，确保异常退出后可恢复

#### 功能三：auto-editor 自动剪辑集成

- **做什么**：集成 auto-editor CLI，提供静音检测和运动检测两种自动剪辑模式，支持基础（阈值+编码器）和高级（8 个开关项+timeline 编辑）配置
- **为什么这样设计**：进一步降低视频剪辑门槛，用户无需手动标注时间点，系统自动检测并剪辑
- **关键设计决策**：将 auto-editor 作为独立任务类型（task_type）集成到现有任务队列中，复用已有的任务控制和进度显示机制，而非单独实现一套流程

### 4.3 系统架构

采用自研 PyWebVue 桥接模式连接 Python 后端和 Vue 3 前端：

- **前端**：Vue 3 Composition API + TypeScript，使用 Composables 替代 Vuex/Pinia 进行状态管理，TailwindCSS + DaisyUI 构建 UI，vue-i18n 支持中英双语
- **后端**：Python 通过 pywebview 创建桌面窗口，`@expose` 装饰器将 Python 方法暴露为 JS API，`_emit()` 实现线程安全的事件推送
- **通信机制**：Vue → bridge.ts → pywebview JS API → Python @expose 方法 → Bridge._emit() → CustomEvent → Vue 事件监听
- **构建打包**：PyInstaller 打包为单目录可执行文件，支持 Windows/macOS/Linux 三平台，macOS 额外支持 .app 应用包格式
- **架构选型理由**：选择 pywebview 而非 Electron，打包体积更小（使用系统原生 WebView），对桌面工具场景更合适

## 5. 开发过程

### 5.1 规划与研究阶段

#### 需求发现

实习期间，我在与同事协作处理视频的过程中逐步发现了几个反复出现的问题。团队每月有大量视频素材需要处理（课程录制、活动记录等），同事们普遍用剪映逐条操作。有一次部门需要统一更新一批视频的片头，几位同事花了一整天手动替换。我主动向主管了解了这块的业务需求，主管提到公司视频量大、更新频繁，希望找到能提升效率的方案，也提到非技术同事在使用 FFmpeg 相关工具时普遍遇到参数配置困难的问题。

我试着帮同事用格式工厂和 HandBrake 配置，却发现这些工具的滤镜选项太基础——一位同事想同时旋转和调整宽高比，配置完后输出文件直接花屏，排查了半天才意识到是参数冲突；编码器列表里二三十个选项，同事们完全不知道区别，问我"到底选哪个"，我也需要查文档才能回答。

类似的情况在身边同学中也存在：课程小组需要批量压缩录像、社团同学需要合并多段视频，但面对 FFmpeg 的参数体系都望而却步。我把这些日常协作中反复遇到的问题做了梳理，归纳出三个核心痛点：

- **现有 GUI 工具不处理滤镜组合冲突**：旋转+宽高比转换等常见组合会导致输出异常，工具本身没有校验和提示
- **编码器选择没有引导**：几十个选项平铺罗列，非技术用户完全不知道该选什么、参数该填多少
- **批处理能力缺失**：即使是相同的操作也要逐条手动执行，无法保存配置模板批量应用

基于这些观察，我确定了 MVP 的功能边界：先聚焦"编码器场景化推荐 + 基础转码 + 批量执行"，滤镜组合冲突和配置复用作为 v2.0 规划。

#### 技术选型

调研了 FFmpegFreeUI、HandBrake、格式工厂、剪映等现有工具的功能覆盖后，我发现它们在滤镜组合冲突处理、编码器场景化推荐、批处理与配置复用三个维度存在明显空白。随后我研究了 pywebview 框架的 API 和限制，评估了 Electron、Tauri、pywebview 三种桌面应用方案，最终选择 pywebview + Vue 3 组合——使用系统原生 WebView 避免打包 Chromium（打包体积从 Electron 方案的 ~150MB 降至 ~30MB），更适合工具类桌面应用。

技术选型确定后，我采用文档先行（Documentation-first）的开发策略，先编写业务规则、状态机定义、数据模型字段等设计文档，再开始编码实现。

### 5.2 MVP 实现（v1.0）

初版于 2026 年 3 月底完成，包含单页面界面、基础文件添加和 FFmpeg 执行、简单命令行预览。我把它发给身边几位有视频处理需求的同事和同学试用，收集到以下反馈：

- **正面反馈**：编码器按"推荐 / 硬件加速"分组后，同事反馈"终于不用纠结选哪个了"，一位同事用推荐编码器成功批量压缩了 20 多个课程录像，耗时从原来逐个用格式工厂的约 40 分钟降至 12 分钟
- **关键缺陷**：几位试用者都反馈"一次性全部执行没法控制，中间有一个卡住了不知道该不该等"，暴露了缺少独立任务控制的痛点；还有人反馈"页面越来越长，找配置项不方便"，指向了单页面架构的可扩展性问题
- **功能请求**：同学提出希望支持添加水印和裁剪片头片尾，同事希望保存常用配置下次直接用

MVP 验证了 PyWebVue 桥接模式的可行性，也明确了架构重构的方向——需要多页面架构承载功能增长，需要任务队列实现独立控制，需要预设系统实现配置复用。

**v2.1 功能完善后**：又推荐给了几位校园媒体社团的同学用。一位社团同学反馈"合并视频时拖拽排序很好用，但想把片头拼到每个视频前面做不到"，我在 Phase 3.5.2 中增加了片头片尾追加功能；另一位同学在 Mac 上运行时 FFmpeg 路径检测失败，促使了 Phase 4 的多平台兼容和数据目录统一迁移。此外，有同学反馈希望有中英文切换，推动了 i18n 国际化支持。

**v2.2 自动剪辑集成**：直接源于一位实习同事的场景——她负责处理直播回放录像，需要把静音片段剪掉以缩短总时长，手动标注时间点非常耗时。我向她推荐了新加的自动剪辑功能，她用基础模式（默认阈值）处理了 10 段直播录像，反馈"检测准确率大约 80-90%，省了大量标注时间"。另一位使用 Mac 的同学反馈应用打不开，促使了 macOS FFmpeg 自动下载和 .app 打包支持。

**v2.2.1~2.2.4 稳定性迭代**：这个阶段主要来自日常使用中暴露的问题。一位同事在处理 20+ 文件时应用突然崩溃（后定位为内存泄漏），另一位 Mac 用户说打开自动剪辑页面时闪了一下红色错误提示（auto-editor 状态初始化竞态），还有人反馈剪辑时输入的时间超过视频总时长导致命令异常。这些问题驱动了线程安全加固、Vue 全局错误处理、剪辑时间范围自动截断等修复。

每次迭代均通过 PR 代码审查流程，19 个 PR 覆盖了从架构重构到缺陷修复的完整变更。

## 6. 项目成果

### 6.1 量化成果

- **功能覆盖**：支持 20+ 编码器（CPU/GPU 硬件加速自动检测）、6 种视频滤镜、4 种剪辑模式、音频字幕混合、多视频合并、自动剪辑共 7 大功能模块
- **代码规模**：后端 ~6,000 行 Python + 前端 ~9,700 行 Vue/TypeScript，30 个 Vue 组件，14 个 Composable，17 个后端模块
- **迭代效率**：6 周内完成 6 个版本迭代，74 次提交，19 个 PR，23 个特性分支
- **跨平台支持**：覆盖 Windows、macOS、Linux 三平台，macOS 支持 .app 应用包格式

## 7. 亮点与挑战

### 7.1 技术挑战

- **挑战一：自研 PyWebVue 桥接层**
  - **背景**：pywebview 的 JS-Python 通信是单向调用模式，Python 无法主动推送事件到前端，而任务进度更新、日志推送等场景需要后端主动通知
  - **方案**：设计了基于队列的 `_emit()` 事件分发机制——Python 端将事件入队，App 层通过 tick 定时器（100ms）刷新队列，通过 `window.dispatchEvent` 推送到前端，实现了线程安全的双向通信
  - **结果**：同事反馈进度条和 FPS 显示流畅，批处理时可以随时查看每个任务的状态，不再需要"等半天不知道跑没跑完"
  - **收获**：深入理解了桌面应用中前后端通信的线程安全问题和事件驱动架构

- **挑战二：线程安全的任务队列**
  - **背景**：v2.0 重构后支持多任务并发执行，但一位同事在同时处理 15 个文件时遇到任务状态显示错乱（暂停的任务显示为运行中），定位为多线程并发导致状态竞争
  - **方案**：Task 模型使用 threading.Lock 保护状态变更方法（append_log/set_progress），TaskQueue 使用原子操作进行 CRUD，队列状态通过原子写入（先写临时文件再 rename）持久化，TaskRunner 使用 ThreadPoolExecutor 管理并发
  - **结果**：修复后该同事重复测试了多批次 20+ 文件并发处理，未再出现状态不一致问题
  - **收获**：系统学习了 Python 多线程编程中的锁、Event、原子操作等并发原语的实际应用

- **挑战三：滤镜组合互斥冲突**
  - **背景**：v2.0 用户测试时，一位同事同时启用了旋转和宽高比转换，输出的视频画面异常。排查发现两个滤镜的参数在 FFmpeg 命令中存在逻辑矛盾，而现有 GUI 工具普遍不处理此类冲突
  - **方案**：在后端 command_builder 中引入互斥规则表，当检测到冲突组合时自动禁用其中一个并给出提示；前端通过实时命令预览让用户直观看到冲突的影响
  - **结果**：v2.1 发布后，参与测试的同学反馈"不用再担心选错参数组合了"，此前频繁出现的输出异常问题未再发生
  - **收获**：认识到在面向非技术用户时，输入校验和冲突处理比功能堆砌更重要

### 7.2 设计亮点

- **实时命令预览**：用户调整任何参数时，前端通过 Bridge API 实时调用后端 command_builder 生成命令并回显，让用户在执行前就能确认命令正确性。引入了防抖（300ms）和 in-flight 保护避免频繁调用

- **Composable 架构模式**：前端使用 14 个 Composable 封装业务逻辑（useTaskQueue、useCommandPreview、useAutoEditor 等），替代 Vuex/Pinia 实现更轻量的状态管理，每个 Composable 职责单一、可测试

- **文档驱动开发**：建立了完整的文档体系（业务规则、状态机、架构、字段定义、开发指南），每次功能开发前先更新文档，确保需求理解和实现一致

### 7.3 开发过程亮点

- **用户驱动的需求优先级**：每次迭代的触发因素都来自真实使用场景——实习期间主动向主管了解公司视频处理的业务需求和效率要求，明确了批处理是刚需；MVP 阶段同事反馈无法控制单个任务，驱动了 v2.0 任务队列的架构重构；同事提出"自动剪掉没声音的部分"，驱动了 v2.2 auto-editor 集成
- **VibeCoding 方法论**：通过 AI 辅助编程，一个人完成了传统需要 2-3 人协作的全栈桌面应用开发，6 周内交付了 7 大功能模块的完整产品
- **PR 审查流程**：即使是独立开发，也坚持通过 19 个 PR 进行代码审查，培养了规范的工程习惯
- **安全意识提升**：在 v2.2.0 ~ v2.2.1 期间主动进行了前后端安全审计，修复了路径穿越、内存泄漏、竞态条件等多类问题

## 8. 项目复盘

### 做得好的方面

- **需求发现前置**：实习期间通过日常协作观察和与主管沟通，在开发前就锁定了核心需求（编码器推荐、滤镜冲突处理、批处理），避免了后期方向偏差。同事用格式工厂时"不知道该选哪个编码器"的场景直接催生了编码器分组推荐功能，成为产品最受好评的特性之一
- **架构重构决策果断**：v1.0 MVP 让身边同事试用后，立即识别到单页面架构和缺少任务控制两个瓶颈，v2.0 果断重构为多页面+任务队列架构，避免了后期更大的技术债
- **文档先行策略有效**：先写文档再编码的工作方式显著减少了返工，状态机文档帮助理清了任务状态变更的复杂逻辑
- **渐进式功能交付**：每个版本聚焦核心功能，先让用户试用再决定下一步方向，避免了"大而全"的风险

### 可改进的方面

- **测试覆盖不足**：项目前期未建立自动化测试体系，主要依赖用户手动测试和代码审查，v2.2.1 时一位同事反馈处理 20+ 文件时应用崩溃（后定位为内存泄漏），如果有自动化测试可能更早发现此类问题
- **性能优化预留空间**：大队列（100+ 任务）场景下的 JSON 序列化性能和多实例并发安全问题尚未完全解决
- **反馈收集不够系统**：目前主要通过微信消息和面对面沟通收集反馈，没有建立结构化的反馈记录机制，部分有价值的反馈可能丢失

### 关键收获

- 系统性理解了桌面应用的全栈开发流程：从用户调研到架构设计到跨平台打包
- 掌握了 Python 多线程编程和线程安全设计的实战经验
- 验证了"日常观察 → 与主管沟通明确需求 → MVP 验证 → 反馈迭代"的产品开发闭环，身边同事和同学的持续反馈让每个功能都有明确的使用场景支撑
- 培养了从用户痛点出发、以解决问题为导向的产品思维，认识到面向非技术用户时，输入校验和冲突处理比功能堆砌更重要
